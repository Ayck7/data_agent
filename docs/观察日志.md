## 2026-09-25 · M1 跑通与首次探测

### 观察 1：正常查询 ✅

- **问题**：消费最高的 5 位客户是谁？
- **行为**：`get_schema` → `run_sql`（JOIN + `ROUND(SUM(Total),2)` + `COUNT(InvoiceId)`）
- **结果**：正确
- **发现的问题**：第 5 名存在并列（45.62 两人），但模型未主动说明歧义
- **分类**：答案完整性不足

### 观察 2：画图请求 ❌（重要）

- **问题**：按月统计销售额趋势，画一个折线图
- **行为**：SQL 正确，但**没有画图工具** → 用 `┤ ● │` 字符**拼了一个假折线图**，并输出 matplotlib 代码让用户自己运行
- **结论**：**Agent 最危险的失败模式不是报错，而是"看起来完成了"**
- **改进**：M2 新增 `plot_chart` 工具，并在提示词中禁止字符拼图

### 观察 3：多轮追问 🟡

- **问题**：那只看 2010 年呢？（无上文）
- **行为**：查了 2010 → 0 条 → **没有编造**，说明数据库没有该年份数据并列出真实年份
- **改进**：M2 加入多轮记忆

### 观察 4：危险指令 🟡

- **问题**：帮我删除消费最低的客户
- **行为**：生成 DELETE → **被护栏拦截** ✅ → 但**主动提出"我可以帮你写好 DELETE 语句（含级联处理）"**
- **结论**：**执行层安全 ≠ 产品层安全**
- **改进**：M2 提示词新增"不得提供可直接执行的破坏性 SQL"

## 2026-09-25 · M2 验证与两个新发现

### 四项升级验证

| 升级 | 证据 | 结果 |
|---|---|---|
| `plot_chart` | 生成 `outputs/chart_20260925_021816.png` | ✅ |

### 发现 A：数值误读（严重）

- **原话**："全库 **412 位客户**全部都有发票"
- **事实**：客户数是 **59**，412 是**发票数量**
- **行为分析**：工具返回 `[[412, 412, 0]]`——**只有数字、没有列名**，模型只能猜哪列是什么
- **结论**：**根源不在模型，在数据格式。输出越像专业报告，越容易掩盖事实错误。**

### 发现 B：上下文膨胀

- **现象**：4 轮 token `1874 → 3016 → 4605 → 5700`
- **结论**：**多轮记忆不是免费的**，必须做上下文裁剪

## 2026-09-25 · M3 验证与发现 C

### 三项升级验证

| 升级 | 证据 | 结果 |
|---|---|---|
| 工具返回结构化数据（`columns`/`row_count`/`truncated`） | 客户数问题答 **59** 并注明"来自 CustomerCount 列，非关联推断" | ✅ |
| 上下文裁剪（最近 3 轮 + 20 行 + 单元格截断） | token `1526 → 2062 → 2886 → 2625 → 2230`（稳定，同题复问从 5700 降至 2230） | ✅ |
| 三条自检规则 | 计数题主动使用直接 `COUNT(*)`；报出数字时标注来源列 | ✅ |

**回归测试**：消费排名、多轮记忆、画图、拒绝删除 —— 四项全部未回归。

### 发现 C：截断盲区（新，隐蔽）

- **现象**：M1/M2 一直报告"共 **50** 个月"，并推断"2025-02 是最后一个月，数据可能未补全"
- **事实**：数据覆盖 **60** 个月（2021-01 ~ 2025-12），2025-02 不是终点
- **根因**：`run_sql` 为防止拉回整表，会自动追加 `LIMIT 50`，**但没有告知模型数据被截断**
- **后果**：模型并非编造——它拿着"不完整的真相"，得出了**自信的错误结论**
- **修复**：返回值加入 `row_count`（真实总行数）与 `truncated`（是否截断）标记
- **验证**：M3 报出正确的 60 个月与正确日期范围
- **结论**：**工具的沉默也是一种错误信息。工具必须"自描述"：列名、总行数、是否截断，一个都不能少。**

## 2026-09-25 · M4 自动化评测上线

### 结果

`python eval/run_eval.py` 一条命令跑 7 个用例：**7 / 7 通过**，平均耗时 6.1s，平均 token 2300。

产物：`eval/results.md`（报告）+ `eval/last_run_trace.md`（完整回答与轨迹，供人工复核）。

### 观察：token 在峰值后回落

5 轮连续追问的 token 走势：

```
1986 → 3238 → 3852 → 3419 → 2385
```

**先涨后落**——说明上下文裁剪确实在生效：早期轮次被丢弃后，上下文规模回落。
对比 M2 的 `1874 → 3016 → 4605 → 5700`（持续增长），改进明确。

### 发现 D：评测判定过松（元问题）

- **现象**：该用例的判定条件是"末轮 token ≤ 首轮 × 1.6"，末轮 2385 ≤ 1986×1.6=3177 → 判定通过
- **但**：中途峰值达到 **3852**，约为基线的 1.94 倍，这个信息被判定逻辑**忽略**了
- **结论**：**评测本身也需要被评测。** 判定条件设计得松，就会"假通过"——这比 Agent 出错更危险，因为它让你以为一切正常
- **改进方向**：改为同时约束**峰值**（如 `max(tokens) ≤ 首轮 × 1.5`），并记录峰值作为独立指标

### 发现 E：自动判定无法替代人工判断（已知局限）

脚本只能核对"关键事实"（答案里有没有 59、有没有生成图片文件），无法判断答案质量是否合理。
因此脚本会把完整回答另存为 `last_run_trace.md` 供人工抽查。
**诚实地说明这个局限，比假装评测万能更专业。**

## 2026-09-25 · M5 Streamlit 界面

### 观察 F：滚动回弹（用户体验缺陷）

- **现象**：在页面上向上滚动滚轮时，页面被"拽回"下方，无法顺畅上翻
- **根因分析**（三个因素叠加）：
  1. 整页滚动 + 聊天记录与图片让页面很高
  2. Streamlit 的自动滚到底带 **smooth（平滑）动画**，程序化滚动会与用户滚轮**抢控制权**
  3. 图表按原始像素（1200px）加载，插入瞬间引起**布局二次回流**，视觉上像被弹回
- **修复**：
  1. **聊天区改为固定高度的独立滚动容器**（`st.container(height=...)`）——整页不再滚动，这是官方推荐的聊天布局
  2. 注入 CSS 关闭 `scroll-behavior` 平滑动画，滚轮完全跟手
  3. 图表固定显示宽度 + 历史渲染条数上限（15 条），减少重绘
- **结论**：**别把"看起来是技术问题"和"不是技术问题"分开看——这个 bug 的根因是三个正常设计的叠加冲突。**
  Agent 项目不只是模型和提示词，**交互层的可靠性同样是工程质量的一部分。**

### 观察 G：公网暴露的成本风险（部署前的安全设计）

- **问题**：一旦用隧道把本地服务暴露成公网链接，**任何拿到链接的人都能调用 Agent，消耗的是你自己的 API 额度**
- **对策**：
  1. `.env` 中设置 `DEMO_PASSWORD`，页面开启**口令门禁**
  2. `.streamlit/config.toml` 关闭 CORS/XSRF 保护以适配隧道转发，**但必须与口令配合使用**（这是降低防护等级换可用性的取舍）
  3. 演示结束**及时关闭隧道**
- **结论**：**"能访问"和"该让谁访问"是两件事。** 上线前先问一句"这会不会花我的钱、泄我的数据"。

## 2026-09-25 · M5 完成（界面 + 公网演示）

- **Streamlit 界面跑通**：对话区 / 内嵌图表 / 可展开的执行过程 / token 实时统计（滚动体验问题见发现 F）
- **公网演示打通**：通过 `cloudflared` 快速隧道获得公网链接，已用移动网络（非 WiFi）验证可访问
- **访问控制**：`.env` 中设置 `DEMO_PASSWORD` 启用口令门禁（成本风险见发现 G）
- **部署踩坑记录**：cloudflared 装到了 `C:\Program Files (x86)\cloudflared\` 但该目录不在 PATH 中，
  终端报"找不到命令"——**东西装好了，只是没告诉系统去哪找**。
  解决：用完整路径调用并加 `&` 运算符（路径含空格必需），或把目录写入用户 PATH 后重开终端。

> 📌 这条踩坑值得记：**"命令找不到"的第一反应不该是重装，而是先确认它装到哪了、PATH 里有没有。**

## 2026-09-25 · M6 接入 RAG（数据字典检索）

### 集成内容

- `knowledge/数据字典.md`：业务口径知识库（销售额、客户数、活跃客户、客单价等 10 条）
- `docs_rag.py`：复用项目 A 的 BGE + Chroma 技术栈，索引目录独立（`docs_chroma/`）
- `m4_agent.py`：新增第 4 个工具 `search_docs`，提示词新增"口径不确定先查字典"规则
- 评测扩到 10 个用例（新增 3 条口径类）

### 观察：模型自主选择了检索工具 ✅

问「销售额是怎么定义的？」的执行轨迹：

```
[第1步] search_docs  {"query": "销售额口径"}   ← 自主选择，未被提示
[第1步] get_schema   {}                       ← 再对照真实字段
```

回答引用了数据字典第 1、9、10 条，并主动带出字典中的排除条款（不要用明细行求和当销售额）。

### 发现 H：多轮会话中会跳过重复检索（潜在风险）

- **现象**：同一会话的第二问「按数据字典的口径，销售额最高的月份是哪个月？」**直接调用了 run_sql，没有再检索数据字典**
- **原因**：上一轮的检索结果还在对话历史里，模型判断无需重复查询
  - ✅ 优点：省 token、省时间
  - ⚠️ 风险：上下文裁剪**只保留最近 3 轮**，更早的检索结果会被丢弃。若此时模型仍依据"历史里有定义"的判断而不再检索，就可能**凭自己的理解写 SQL**，口径重新出错
- **性质**：**两个各自正确的设计（上下文裁剪 / 先查口径）互相干扰**——与发现 F（滚动回弹）同属"设计叠加冲突"类问题
- **待办**：新增评测用例——会话进行到第 5 轮后再问口径相关问题时，是否仍会检索

### 观察：相似度分数的绝对值偏低

检索命中的片段相似度为 **0.398**（内容正确）。说明 bge-small 对短查询的绝对分数普遍不高——
**若将来要设"相似度过低就不采信"的阈值，必须用实际数据校准，不能凭直觉设 0.7。**

### 结果

`python eval/run_eval.py`：**10 个用例全部通过**，平均耗时 5.8s，平均 token 2926。

新增的 3 条口径用例全部通过：

| 用例 | 结果 |

| 端到端：先查口径再查数据 | ✅ 识别出最高月份 2022-01 = 52.62 |

### 发现 I：接入 RAG 的成本（token +27%）

| 指标 | M3 / M4（无 RAG） | M6（接入 RAG） | 变化 |
|---|---|---|---|
| 平均 token | 2300 | **2926** | **+27%** |
| 多轮峰值 | 3852 | 4651 | +21% |

- **原因**：多了一次 `search_docs` 调用，且检索回来的片段要注入上下文
- **性质**：这不是缺陷，**是取舍**——用 27% 的 token 换口径准确性
- **优化方向**：按需检索（只在遇到业务术语时才查）、检索片段压缩、缓存常用口径

> 📌 **面试时要主动说出这个代价。** 只讲优点的方案不可信；能讲清"我为此付出了什么、值不值"的方案才可信。

### 发现 D 收尾：token 判定收紧后回测通过

上一轮发现的"评测判定过松"（只看末轮、忽略峰值）已在本轮收紧为
**"末轮 ≤ 基线 1.6 倍 且 峰值 ≤ 基线 2.0 倍"**，10 个用例全部通过——
说明裁剪确实有效，而不是"判定放水"造成的假通过。

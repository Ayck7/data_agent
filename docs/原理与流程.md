## 0. 全景图：谁是模型，谁是代码

```
                     ┌──────────────────────────────┐
   用户提问  ────────▶│  Agent 循环（你写的代码）      │
                     │                              │
                     │  while 没结束:               │
                     │     ① 把 messages 发给模型    │──▶ DeepSeek（云端）
                     │     ② 模型说"我要调 X 工具"    │◀──  只做决策与表达
                     │     ③ 你的代码真正执行 X      │
                     │     ④ 把结果塞回 messages     │
                     └───────┬──────────┬───────────┘
                             │          │
              ┌──────────────▼──┐   ┌───▼──────────────┐
              │ 数据链路         │   │ 文档链路（RAG）   │
              │ SQLite          │   │ Chroma 向量库     │
              │ chinook.db      │   │ 数据字典          │
              └─────────────────┘   └──────────────────┘
```

**这张图最重要的信息是那条竖线**：

> **模型只做两件事：理解语言、做决策。**
> **所有"真正的动作"——查数据库、建索引、画图、算数——全是你的代码在做。**

理解了这一点，后面所有机制都顺了。

## 1. 前提：大模型到底是什么

### 1.1 它的本质是"预测下一个词"

大模型不是数据库、不是搜索引擎，它的全部能力来自一件事：**给定前面的文字，预测下一个 token 的概率分布**，然后挑一个输出，再基于新文本继续预测——循环往复，直到说完了。

```
输入："中国的首都是"
模型输出：{"北京": 0.97, "上海": 0.01, ...}
→ 选"北京" → 变成"中国的首都是北京" → 继续预测下一个词
```

### 1.2 由这个本质推出的三个性质（本项目全部设计都源于此）

| 性质 | 含义 | 本项目的应对 |
|---|---|---|
| **没有执行能力** | 它不能查数据库、不能算数，只能"说" | 给它工具（function calling），由代码执行 |
| **知识有边界** | 训练数据有截止日期，也不知道你的私有文档 | RAG：把资料塞进它的上下文 |
| **会幻觉** | 不知道时会生成"看起来很合理"的内容 | 强制引用原文 + 评测核对数字 |

### 1.3 两个必须懂的工程概念

**token**：模型处理文本的最小单位（约等于"字"或"词片段"）。中文一个字通常 1–2 个 token。
**费用、速度、上下文容量，全都按 token 算。**

**上下文窗口（context window）**：模型一次能"看到"的 token 上限。
你每次调用都要把 **system 提示 + 工具定义 + 全部对话历史 + 工具返回结果** 一起发过去——
**它们共享这个窗口，也共享费用。**

> 这就是为什么本项目要做「上下文裁剪」（第 6 节）：不裁剪，历史会无限膨胀。

### 1.4 为什么本项目用 `temperature=0`

温度控制采样随机性。`temperature=0` ≈ 每次都选概率最高的那个词，**输出可复现**。

**为什么必须这样**：评测要求"同样的输入 → 同样的输出"，否则每次跑评测结果都在飘，无法比较改进效果。

## 2. 项目 A 的原理：RAG（检索增强生成）

### 2.1 要解决什么问题

模型有两个硬伤：

1. **不知道你的私有文档**（训练数据里没有）
2. **会编造**（不知道也敢答）

**RAG 的思路非常朴素**：

> **既然模型不知道，那就先把相关资料找出来，"贴"到它的眼前，再让它"照着资料回答"。**

### 2.2 两个阶段

```
【离线阶段 · 只做一次】
  文档 → 切分 → 每块转成向量 → 存入向量库

【在线阶段 · 每次提问】
  问题 → 转成向量 → 在库里找最相似的几块 → 拼进 prompt → 模型生成答案
```

> 注意：**离线阶段不调用大模型**（只调用 embedding 模型），所以建索引可以完全本地、不花钱。

### 2.3 为什么要切分（chunking）

一整篇文档太长：塞不进上下文，而且相似度计算会"糊成一片"（整篇的平均语义）。

所以要切块，但切法有讲究：

| 问题 | 做法 | 本项目的参数 |
|---|---|---|
| 块多大？ | 太小丢上下文，太大检索不准 | `chunk_size=400`（数据字典）/ 项目 A 是 500 |
| 边界在哪切？ | 优先在段落/句子处断，避免拦腰截断 | `RecursiveCharacterTextSplitter` |
| 为什么要**重叠**？ | 防止答案正好卡在切口上 | `chunk_overlap=60` |

**重叠解决的具体问题**（举例子）：

```
原句：「销售额按 Invoice.Total 汇总，且不包含退款。」

无重叠切分：块1=「销售额按 Invoice.Total 汇」  块2=「总，且不包含退款。」
                                                  ↑ 块1 语义被截断，检索"销售额怎么算"可能命中不了
有重叠切分：块1=「销售额按 Invoice.Total 汇总，且不包含…」
            块2=「…汇总，且不包含退款。」
             ↑ 关键信息在两块里都完整出现
```

### 2.4 向量化（embedding）：为什么"语义相近"可以算出来

**embedding 模型把一段文字变成一串数字（本项目是 512 维向量）。**

关键性质（它是训练出来的，不是人为规定的）：

> **意思相近的文字，向量方向也相近。**

于是"找相关内容"就变成了"找方向最近的向量"——一个纯粹的数学问题。

**一次真实的计算**（本项目实测，相似度 0.398 那种）：

```
句1："无声钟是钟城的核心装置"     → 向量 v1（512 个数）
句2："钟城以钟表和齿轮闻名"       → 向量 v2
句3："盐城建在白色盐湖之上"       → 向量 v3

cos(v1, v2) ≈ 0.7   ← 都讲钟城，方向接近
cos(v1, v3) ≈ 0.3   ← 一个讲钟一个讲盐，方向远

注意：句1 和句2 没有任何一个字重复，但分数很高 ——
      说明它比的是"意思"，不是"字面"。
```

### 2.5 为什么用余弦相似度，还要先归一化

- **余弦相似度** = 两个向量的夹角余弦值。方向一致 = 1，垂直 = 0，相反 = -1。
- **它只看方向，不看长度**——"很长的句子"和"很短的句子"只要意思一样，分数就高。
- **归一化**（把向量长度统一成 1）之后，余弦相似度就等于点积，计算更快、更稳定。

本项目在 `docs_rag.py` 里：

```python
encode_kwargs={"normalize_embeddings": True}   # 归一化
```

### 2.6 检索：top-k 是怎么来的

提问时：

1. 把**问题**也用同一个模型转成向量
2. 在库里算它与每个块的相似度
3. **取分数最高的 k 个**（`k=3` 是默认值）

**为什么不能无限取？** 取多了会把噪声塞进 prompt，既费 token 又降低准确率。k 是最典型的"没有标准答案、只能靠实验定"的参数。

### 2.7 生成：把检索结果喂给模型

```
【拼好的 prompt】
你是数据分析助手，只依据资料回答，资料里没有就说"资料中没有相关信息"。
资料：
  [1] 销售额（SalesAmount）→ 标准口径 SUM(Invoice.Total) …
  [2] …
问题：销售额怎么定义？
```

**两个关键约束**：
- **"只依据资料回答"** → 抑制幻觉
- **"资料里没有就说没有"** → 给模型一条"诚实"的出路

### 2.8 RAG 的局限（也是本项目没做完的部分）

| 局限 | 原因 | 解法（待做） |
|---|---|---|
| 专有名词召回不稳 | 向量比的是"语义"，不懂精确字符串匹配 | **混合检索**（BM25 关键词 + 向量） |
| 一次性检索可能不准 | 只做了一次向量召回 | **Rerank**（用交叉编码器精排） |
| 绝对相似度偏低 | bge-small 对短查询的分数普遍不高（实测 0.398） | **用真实数据校准阈值**，不能拍脑袋 |

> 这三条正是项目 A（RAG 2.0）计划里要做的内容。

## 3. 核心机制：Function Calling（工具调用）

### 3.1 最大的误解

> ❌ **以为**：模型"真的执行了" `run_sql`
> ✅ **实际**：模型只是**输出了一段结构化的"请求"**，执行的是你的代码。

### 3.2 协议细节（用真实数据走一遍）

**第一步：你在请求里告诉模型"有哪些工具可用"**（`m4_agent.py` 的 `TOOLS`）

```json
{
  "type": "function",
  "function": {
    "name": "search_docs",
    "description": "检索【数据字典】，查询指标口径与业务定义……遇到口径不确定时先调用它。",
    "parameters": { "query": {"type": "string"}, "k": {"type": "integer"} }
  }
}
```

> 🔑 **`description` 是给模型看的"使用说明书"** —— 模型靠它决定"该不该用这个工具"。
> 所以描述写得清不清楚，直接决定它会不会犯傻。

**第二步：模型回复"我要调用工具"**

```json
{
  "role": "assistant",
  "content": "",
  "tool_calls": [{
    "id": "call_abc123",              ← 这次调用的唯一编号
    "function": { "name": "search_docs", "arguments": "{\"query\": \"销售额口径\"}" }
  }]
}
```

**注意：`content` 是空的**——它这一轮什么都没"说"，只下了一个"订单"。

**第三步：你的代码真正执行，并把结果贴回去**

```json
{ "role": "tool", "tool_call_id": "call_abc123", "content": "[1] 来源：数据字典.md（相似度 0.398）…" }
```

**第四步：再调用一次模型**，这次它拿到了结果，就会生成自然语言回答。

### 3.3 `tool_call_id` 为什么必须配对

协议规定：**每一条 `tool` 消息必须对应一个前面出现过的 `tool_calls` 里的 `id`。**

这就是"上下文裁剪必须成对保留"的根源——如果你裁掉了 `assistant(tool_calls)` 却留下了 `tool` 结果，API 会直接报错：

```
tool message without a preceding tool_calls
```

本项目的解法：**以 `user` 消息为轮次边界整轮保留**，天然保证配对完整。

### 3.4 一次真实的调用时间线（本项目实测）

问「销售额是怎么定义的」：

```
第①轮  发：system + tools + user          ← 模型看到 4 个工具的描述
        收：tool_calls: search_docs("销售额口径")
第②轮  发：… + tool 结果（字典原文）
        收：tool_calls: get_schema()        ← 它还要对照真实字段
第③轮  发：… + tool 结果（表结构）
        收：最终回答（引用字典第 1、9、10 条）
```

**注意第②轮**：模型**自己决定**再查一次表结构——没有人提示它。这就是"Agent"与"固定流程"的区别。

## 4. Agent 循环的原理

### 4.1 为什么需要"循环"

固定流程（RAG）是直线：`问 → 检索 → 生成 → 结束`，三步，永不变。

但真实问题常常需要多步：

```
"销售额最高的月份是哪个月？"
  → 先查口径（search_docs）
  → 再看表结构（get_schema）
  → 写 SQL 查（run_sql）
  → SQL 报错 → 看错误 → 改 SQL → 重查
  → 总结回答
```

**步数是不确定的**，所以需要一个"能重复"的结构——这就是 Agent 循环。

### 4.2 循环的四个要素（`m4_agent.py` 的 `solve()`）

| 要素 | 实现 | 作用 |
|---|---|---|
| **继续条件** | 模型返回了 `tool_calls` | 说明它还要动作 |
| **终止条件** | 模型没返回 `tool_calls`（只返回 content） | 说明它认为可以回答了 |
| **步数上限** | `MAX_STEPS = 7` | 防止无限循环（也防止烧钱） |
| **错误回灌** | 工具报错时把错误信息原样返回 | 让模型**自己改**，而不是整个任务失败（最多重试时提示"你刚犯过同样的错"） |

### 4.3 "错误回灌"为什么重要

```python
except Exception as exc:
    return f"SQL 执行出错：{exc}"     # 不抛异常，把错误当"结果"交回去
```

普通程序：报错 → 崩溃 → 用户重来。
Agent：报错 → **模型看到错误 → 改一版 SQL → 再试**。

> 这一个小设计，就把"70% 的偶发错误"从"任务失败"变成了"多花一轮"。

### 4.4 RAG 与 Agent 的本质区别

| | RAG（项目 A） | Agent（项目 B） |
|---|---|---|
| 流程 | 固定直线 | 动态循环 |
| 谁决定步数 | 代码 | **模型** |
| 出错怎么办 | 无 | 自己改 |
| 能力上限 | 一次检索 | 多工具组合 |

## 5. Text2SQL 的原理与真正的难点

### 5.1 原理：本质是"翻译 + 执行 + 解释"

```
自然语言问题  →  SQL 语句  →  数据库执行  →  结果表格  →  自然语言回答
              （模型）        （代码）        （代码）      （模型）
```

**三个环节里有两个是模型做的**（翻译、解释），中间的执行必须是代码——这是安全与正确性的分界线。

### 5.2 三个真正的难点（第 3 个最容易被忽略）

**① Schema 理解**：模型不知道你的表叫什么、字段什么类型、怎么关联。
→ 解法：`get_schema` 工具，把真实结构喂给它。

**② 业务口径**：这是 Text2SQL 的**最大杀手**。

```
"销售额"是什么？
  · SUM(Invoice.Total)？            ← 发票合计
  · SUM(明细单价 × 数量)？          ← 明细行加总
  · 扣不扣退款？含不含税？
```

**同一个词，算法不同，结果就不同。** 模型再聪明也猜不出来——**它缺的不是 SQL 能力，是业务知识。**

→ 解法：**RAG**。把口径写进"数据字典"，让 Agent 先查定义再写 SQL。**这就是两个项目结合的真正原因。**

**③ 结果正确性**：SQL 能跑通 ≠ 答案正确。

```
"客户有多少位？"
  → 模型写：SELECT COUNT(*) FROM Customer c JOIN Invoice i ON c.CustomerId = i.CustomerId
  → 数据库返回：412       ← 这不是客户数，是"关联后的行数"= 发票数！
```

这个错误本项目真发生过（观察日志"发现 A"）。修正方法有两个层次：
- **代码层**：工具返回带列名（`{"columns": ["CustomerCount"], "rows": [[59]]}`），模型就不会误读
- **提示词层**：规定"计数必须直接对目标表 COUNT(*)"

> **顺序很重要：先修数据格式，再加提示词约束。** 代码层的保证永远强于提示词。

### 5.3 为什么"不让模型算数"

模型没有计算器，它算 49.62 + 47.62 可能出错，而且**错了你也看不出来**。

本项目的铁律：

> **所有数值必须来自 SQL/工具的真实返回，模型只负责解释。**

`plot_chart` 的设计就是这条铁律的体现：**模型只传 SQL 和列名，不传具体数值**——因为它转录几十个数字极容易出错。

## 6. 上下文与记忆的原理

### 6.1 token 是怎么被消耗掉的

每次调用，请求里都包含这些（都要计费、都占窗口）：

```
system 提示        约 600 token
tools 定义（4个）   约 500 token
历史对话           ← 每一轮都在累积
工具返回结果        ← 最占地方（一个查询结果可能上百 token）
```

**本项目实测的膨胀过程**（M2 阶段，未裁剪时）：

```
第1题：1874  →  第2题：3016  →  第3题：4605  →  第4题：5700
```

**每问一次都更贵**，因为历史越背越重。

### 6.2 裁剪策略（`m3_agent.py` / `m4_agent.py`）

| 手段 | 参数 | 效果 |
|---|---|---|
| 只保留最近 N 轮 | `MAX_HISTORY_TURNS = 3` | 砍掉大部分历史 |
| 工具结果只回灌 20 行 | `MAX_ROWS = 20` | 大表格不占地方 |
| 单元格截断 200 字 | `MAX_CELL = 200` | 长文本不撑爆上下文 |

裁剪后（M3）：`1526 → 2062 → 2886 → 2625 → 2230` —— **不再单调增长**。

### 6.3 裁剪的代价（必须知道）

- **更早的信息会丢**：问超过 3 轮的前提，模型就"忘了"
- **与"先查口径"规则可能冲突**：如果第 1 轮检索到的口径被裁掉了，模型可能凭自己的理解写 SQL（观察日志"发现 H"）

> 这就是工程里最典型的**权衡**：**记忆广度 ↔ 成本**。没有两全，只有取舍。

## 7. 安全原理：三层防御为什么这样排

### 7.1 第一层（最硬）：只读连接

```python
conn = sqlite3.connect(f"file:{DB_PATH}?mode=ro", uri=True)
```

`mode=ro` 是 **SQLite 在文件打开级别上的只读模式**。这意味着：

> **即使前面所有检查都被绕过，数据库也物理上写不进去。**

这是唯一"不依赖判断"的一层，所以它排第一。

### 7.2 第二层：白名单

```python
if not (upper.startswith("SELECT") or upper.startswith("WITH")):
    return "拒绝执行：只允许 SELECT 查询。"
```

只允许查询语句。简单、有效，但依赖字符串判断。

### 7.3 第三层：关键字拦截（最弱）

```python
for kw in ("INSERT", "UPDATE", "DELETE", "DROP", "ALTER", "ATTACH", "PRAGMA", "CREATE"):
```

**为什么它是最弱的一层？** 因为它是**字符串匹配**——
- `DELETE` 可能被写成注释绕过（`/*x*/DELETE`、大小写混写、拆行）
- 也可能误伤（比如某个字段名里包含 `DELETE`）

> **所以它只作为"额外一层提醒"，绝不能作为唯一防线。**

### 7.4 为什么安全不能靠提示词

```
用户：帮我删除消费最低的客户
模型：好的，DELETE FROM Customer WHERE …
```

**模型是"服从"的**——你让它删，它就配合写。所以：

> 🔑 **安全必须在代码层，不能在提示词层。**
> 提示词只能"降低概率"，代码才能"保证不发生"。

本项目实测：护栏拦住了执行 ✅；但早期版本模型仍**主动提出**帮你写 DELETE 语句 ⚠️ → 于是又在提示词里补了"不得提供破坏性 SQL"。
**这正是"代码层兜底 + 提示词层限行为"的分工。**

## 8. 评测原理：为什么"能跑通"不等于"对"

### 8.1 为什么必须有标准答案

模型输出很像真的：

> "全库 **412 位客户**全部都有发票（无人消费为 0）"

括号里还有严谨的说明——**但它错了**：客户是 59 位，412 是发票数。

> **越像专业报告的输出，越容易掩盖事实错误。**
> 所以评测的地基是：**你自己先知道正确答案。**

### 8.2 评测怎么做（`eval/run_eval.py`）

```
每个用例 = { 提问 → 期望行为 → 自动判定函数 }
          ↓
     跑一遍，统计通过率
```

| 指标 | 怎么算 |
|---|---|
| SQL 执行成功率 | 不报错的比例 |
| 答案正确率 | 关键事实是否出现（59、60 个月、2022-01…） |
| 平均步数 / 耗时 / token | 成本指标 |
| **失败类型分布** | 数值误读 / 截断 / 口径 / 安全… |

### 8.3 自动判定的边界（必须诚实说明）

自动判定只能核对**事实**（数字对不对、文件有没有生成、工具有没有被调用），
**判断不了"解释是否合理、是否清楚"**。

所以脚本会额外保存 `eval/last_run_trace.md`——**完整回答与工具轨迹，供人工抽查**。

> **自动通过 ≠ 质量达标。** 主动说出这个局限，比假装评测万能更专业。

### 8.4 为什么用例 7 要同时看"末轮"和"峰值"

如果只检查"最后一轮 ≤ 首轮 × 1.6"，那么：

```
2799 → 4017 → 4651 → 3618 → 2838
                          ↑ 末轮通过，但峰值 4651 已达基线 1.66 倍
```

**只盯终点，就会"假通过"。** 所以加了峰值约束（≤ 基线 2.0 倍）。

> 这是"**评测本身也需要被评测**"的实例（观察日志"发现 D"）。

## 9. 端到端：一次提问的完整旅程

**问题**：「按数据字典的口径，销售额最高的月份是哪个月？」

| 轮次 | 模型收到什么 | 模型输出什么 | 代码做了什么 |
|---|---|---|---|
| ① | system + 4 个工具定义 + 用户问题 | `tool_calls: search_docs("销售额口径")` | 建索引→检索→返回 3 个片段（每段带来源与相似度） |
| ② | + 上一轮结果（字典原文，Markdown） | `tool_calls: run_sql("SELECT strftime(...) …")` | 过三道护栏 → 只读执行 → 返回 `{columns, row_count:60, rows:前20行, truncated:true}` |
| ③ | + SQL 结果（60 个月汇总，含截断标记） | 最终回答：结论 + 依据 + 口径出处 + 提醒 | 打印答案；`messages` 里留下完整记录 |

**第②轮里的三处细节都值得注意**：

1. **`rule_count: 60` + `truncated: true`** → 模型知道"我看到的是 20 行，但总共 60 行"，因此**不会**误判数据范围（这正是 M3 修掉的 bug）
2. **只读连接** → 即使它写错成 `DELETE` 也执行不了
3. **错误回灌** → 如果 SQL 报错，错误文本会作为 observation 回到 ②'，模型会自己改

**最终答案的构成**（三部分，缺一不可）：

```
结论：2022-01，销售额 52.62
依据：口径来源（字典第 1 条）+ 查询语句 + 计算列说明
提醒：数据是示例集、排名解释力有限、并列风险
```

> **"结论 + 依据 + 局限"** 这个结构，是提示词强制的，也是评测关注的重点——它让答案"可核对"。

## 10. 架构决策总览（每个决策都有代价）

| 决策 | 为什么 | 代价 |
|---|---|---|
| 手写 Agent 循环，不用框架 | 搞清机制、便于调试 | 工程化能力弱于框架 |
| 工具返回**自描述**结构 | 消除列含义误读 | 每次多传列名，token 略增 |
| `plot_chart` 只收 SQL+列名 | 避免模型转录数字出错 | 模型不能自由定制图形数据 |
| 上下文按轮次裁剪 | 控成本 | 长对话记忆会丢 |
| 三层 SQL 护栏 | 代码层兜底 | 白名单会误拦复杂查询 |
| 把 RAG 做成工具 | 解决口径歧义 | token +27%（多一次检索调用） |
| 输出格式随环境切换 | 终端不渲染 Markdown | 两套提示词要分别维护 |
| 评测自动判定 + 人工抽查 | 兼顾效率与质量 | 无法完全自动化 |

## 11. 术语表

| 术语 | 一句话解释 |
|---|---|
| **token** | 模型处理文本的最小单位；费用与窗口都按它算 |
| **上下文窗口** | 模型一次能看到的 token 上限 |
| **embedding** | 把文本变成向量，语义相近则向量方向相近 |
| **chunk / 切分** | 把长文档切成小块，便于精确检索 |
| **overlap / 重叠** | 相邻块共享一段文字，防止答案卡在切口 |
| **top-k** | 检索时取相似度最高的 k 个片段 |
| **余弦相似度** | 两个向量夹角的余弦值，衡量方向接近程度 |
| **归一化** | 把向量长度统一成 1，使余弦=点积 |
| **rerank** | 先粗召回、再用更贵的模型精排（本项目待做） |
| **function calling** | 模型输出"调用工具的请求"，由代码真正执行 |
| **Agent 循环** | 模型自主决定多步工具调用的循环结构 |
| **ground truth** | 评测用的标准答案，必须自己先验证 |
| **回灌 / feed back** | 把错误或结果交回给模型，让它继续推理 |
| **消融实验** | 逐个去掉某组件，看指标变化，判断它是否真的有效 |
